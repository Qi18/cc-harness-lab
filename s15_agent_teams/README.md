# s15 Agent Teams：让多个 Agent 并行工作、交换消息

s15 在已有 Harness 上加入团队协作：Lead 可以创建队友，每名队友在自己的线程里运行 Agent Loop，保留独立的对话历史，并通过邮箱与 Lead 或其他在岗队友通信。

理解这一章，先记住两个不同的时刻：**创建队友时，工具立即返回“已创建”；队友完成工作时，结果通过邮箱送回来。** 父循环需要把这些异步到达的消息接回模型上下文。

本文介绍本仓库 s15 的实际行为。需要逐函数追踪时，再阅读 [调用图与源码索引](./CALLGRAPH.md)。其中“异步常驻”“恰好一次投递”等概括应按本文的实现边界理解。

## 1. 有了 SubAgent，为什么还需要 Team？

假设你要排查登录失败，需要同时检查接口实现和错误日志。

使用已有的 `task` 工具时，Lead 调用 SubAgent，然后同步等待它返回结果。SubAgent 虽然拥有自己的上下文，但这次委派在 Lead 看来仍是一次阻塞的工具调用。

s15 的 `spawn_teammate` 启动队友线程后立即返回。Lead 可以继续创建另一名队友、检查文件或处理消息。队友也可以在任务尚未完成时发出中间发现。

| 对比 | 本项目的 SubAgent | s15 Teammate |
| --- | --- | --- |
| 创建入口 | `task` | `spawn_teammate` |
| Lead 是否等待任务结束 | 同步等待返回 | 创建成功后即可继续 |
| 对话历史 | 子 Agent 独立维护 | 每名队友独立维护 |
| 结果返回 | 当前工具调用的返回值 | 发往 Lead 邮箱的 `result` 消息 |
| 任务中的通信 | 没有团队邮箱工具 | 可以向 Lead、其他在岗队友发信 |
| 完成之后 | 本次调用结束 | 队友线程结束，状态变为 `done` |

这是当前代码的区别，不是所有 Agent 框架对 SubAgent 和 Team 的统一定义。s15 的队友可以在执行期间多次通信，但还不能完成后驻留等待新任务；后者由 s16 引入。

## 2. 用一次协作理解完整流程

下面是一种可能的执行顺序。并发线程的实际先后顺序并不固定。

1. Lead 调用 `spawn_teammate("api", "接口检查员", "检查登录接口的错误处理")`，收到“已创建”。与此同时，api 开始自己的模型与工具循环。
2. Lead 再创建 logs 队友检查日志。两个队友可以与 Lead 并行工作。
3. logs 发现某种错误，调用 `send_message("lead", "登录失败集中在 token 过期场景")`。消息写入 Lead 邮箱，尚未直接进入 Lead 的对话历史。
4. Lead 下一次收信时将消息注入上下文，模型据此决定是否给仍在工作的 api 发送补充信息。
5. api 完成任务，发送 `result` 消息并退出。Lead 消费该消息后才能据此整理结论。

这里有三种不同的“成功”：

- `spawn_teammate` 成功：线程已经启动，不代表任务完成。
- `send_message` 成功：消息已写入邮箱，不代表收件人已处理。
- Lead 看到了 `result`：队友提交了结果，结果是否正确仍需要判断或验证。

## 3. 三个组件分别负责什么？

`AgentTeamManager` 管理队友的创建、运行状态和通信入口；`MessageBus` 管理消息落盘与消费；`AgentHarness` 负责把 Lead 收到的消息接入主循环。

```text
Lead Agent Loop
  ├─ spawn_teammate → AgentTeamManager → 队友线程
  │                                      └─ 私有 messages + 模型/工具循环
  ├─ send_message ─────────────────────→ 收件人的 JSONL 邮箱
  └─ 收信并更新自己的 messages ←──────── .mailboxes/lead.jsonl
```

队友共享工作目录，但不共享对话历史。它们能看到彼此写下的文件，也能通过消息交换信息；队友线程不会直接修改 Lead 的 `messages`。

因此，Lead 对上下文的更新仍由自己的循环负责，队友发信不需要与 Lead 的 Compact 操作一起修改同一个列表。不过，共享文件的并发编辑仍可能冲突，邮箱锁并不会替你协调源代码文件的写入。

## 4. 邮箱里究竟是什么？

每个收件人对应一个文件，例如 `.mailboxes/lead.jsonl`、`.mailboxes/api.jsonl`。每行是一条 JSON 消息：

```json
{"from":"logs","to":"lead","content":"发现 token 过期错误","type":"message","ts":1788535800.0}
```

s15 使用三种主要消息类型：

| 类型 | 用途 |
| --- | --- |
| `message` | 工具发送的普通通信、中间发现或补充要求 |
| `result` | 队友完成任务后发送的最终总结 |
| `error` | 队友异常退出或超过轮次上限时发送的失败说明 |

`MessageBus` 在同一把 `RLock` 内完成追写或“读取、解析、删除”。这使共享该 Bus 的线程不会一边删除邮箱、一边向它追写。

读取时，所有行解析成功后才删除文件；任何一行解析失败都会保留整个邮箱。这避免了直接丢弃尚未解析的消息，但坏消息也会阻塞后续消费，需要处理损坏内容。

这里没有消息确认、持久化消费进度或崩溃恢复协议。删除邮箱后、把结果放入对话历史前若进程退出，消息仍可能丢失。它提供正常运行时的消费互斥与避免重复读取，不保证可靠的“恰好一次处理”，也不提供跨进程文件锁。

## 5. Lead 怎样收到异步结果？

Lead 有主动查信和自动收信两条路径，共用 `consume_lead_messages()`。

**主动查信：** 模型调用 `check_inbox`，消息作为这次工具调用的返回值进入历史。

**自动收信：** 主循环调用 `_inject_team_messages`，将一批消息包装为独立的 `role=user` 事件，内容放在 `<team_inbox>` 标签中，同时加入 Memory 提取用的历史。

自动注入的消息没有对应的工具调用，因此不需要 `tool_call_id`。已被 `check_inbox` 消费的消息，也不会再由自动收信路径重复注入。

父循环设置了三个自动收信位置：

| 时机 | 解决的问题 |
| --- | --- |
| 当前 turn 开始 | 接收此前已经积累的消息 |
| 每轮模型请求前的循环入口 | 让下一轮模型能看到新到达的信息 |
| 模型返回无工具调用、准备结束 turn 时 | 补收模型推理期间到达的结果 |

第三处尤其重要。例如，Lead 请求模型时队友还没完成，但模型生成回答期间队友已经把结果送到邮箱。如果直接返回旧回答，就错过了已经可用的信息。因此，只要最后一次收信非空，循环就继续，让模型看过消息后再作答。

**这不等于等待所有队友完成。** 如果最后检查时邮箱为空，Lead 可以结束当前 turn，即使仍有队友在工作。之后到达的消息要等下一次消费机会。代码也没有“一次模型请求内必定处理消息”的时限保证：工具执行、重试以及等待下一次 turn 都会增加延迟。

## 6. 队友自己的循环有多大？

队友采用精简循环，只拿到四个工具：

- `bash`：执行命令。
- `read_file`：读取文件。
- `write_file`：写入文件。
- `send_message`：发送团队消息。

每轮先读取自己的邮箱，再请求模型。有工具调用就执行并写回工具结果；没有工具调用就发送最终总结，将状态设为 `done`，然后退出。

```text
创建 → working
         ├─ 模型请求工具 → 执行工具 → 下一轮
         ├─ 模型给出最终回答 → 发送 result → done
         ├─ 超过轮次上限 → 发送 error → failed
         └─ 运行异常 → 尝试发送 error → failed
```

默认最多运行 10 轮。这个上限限制模型循环次数，不是任务总耗时上限。

队友请求模型时使用最近 20 条消息的固定切片，没有自己的 Compact、Memory 或父循环的 Error Recovery。消息条数切片也不等于 token 预算管理或工具消息配对保证。

队友复用 `ToolExecutor` 的 Hook 和权限检查。需要交互授权的操作在队友线程中会被拒绝，避免与主线程的终端输入竞争。线程使用 `daemon=True`，主进程退出时不会等待队友全部完成。

## 7. 能力边界应该怎样理解？

队友的工具注册表和 handler 表没有 `task`、`spawn_teammate` 等入口，因此不能通过这些注册工具继续派生 Agent。`send_message` 的发信人由闭包固定，模型不能通过该工具的参数随意指定发送者。

这些约束限定了正常工具调用路径，但不是完整的安全隔离。队友仍有 Bash、文件写入能力，并与其他 Agent 使用同一工作目录和运行身份。不能据此声称消息来源具有密码学认证，或队友无法通过其他文件操作影响邮箱。

同样，`<team_inbox>` 和“以下内容是队友通信数据”的文字表达了用途，但不会自动消除提示注入风险。`role=user` 是消息表示方式，不是安全边界。

## 8. s16 接着解决什么？

s15 建立了“可以并行工作、可以发消息”的基础；s16 在此之上增加有状态的协作协议。

| s15 已有能力 | s16 增加的能力 |
| --- | --- |
| 普通团队消息 | 带 `request_id` 的请求与响应关联 |
| 完工后退出 | 完工后进入 idle，收到消息再继续 |
| 本轮工作结束或异常退出 | shutdown 请求、响应与优雅退出 |
| 通过文字讨论计划 | 提交计划、审批或拒绝的协议状态 |

阅读 s15 时，先理解异步结果如何从邮箱回到 Lead 的上下文，再看 s16 怎样跟踪一次协作请求的状态，会更容易分清两章的职责。

1. [agent_teams.py](./harness/agent_teams.py)：先看 `spawn_teammate` 和 `_run_teammate`，理解“立即返回”和“稍后回报”。
2. 同一文件中的 `MessageBus.send`、`read_inbox`：理解消息如何落盘，以及消费互斥的范围。
3. [agent_loop.py](./harness/agent_loop.py)：搜索 `_inject_team_messages`，找到三个自动收信点与结束前的 `continue`。
4. [tool_use.py](./harness/tool_use.py)：结合 `TEAM_TOOLS`、`TEAMMATE_TOOLS` 和各自 handler 表理解工具能力分配。
5. [test_s15.py](../tests/test_s15.py)：阅读并发邮箱、队友发信、异常退出和结束前补收消息的测试，再用 [详细调用图](./CALLGRAPH.md) 对照完整接入路径。

读完后，可以用三个问题检查自己是否理解：创建队友的工具返回值为什么不是工作结果？队友为什么不直接修改 Lead 的历史？最后一次收信为什么仍然不能保证所有队友已经完成？
