# s14 Cron Scheduler：到时间后，让 Agent 自动开始工作

s14 为 Harness 加入本地定时调度：模型登记一条时间规则和任务 prompt；到期后，调度器将 prompt 放入队列；Agent 空闲时自动处理它。

它调度的是交给模型的任务要求，而不是直接交给操作系统执行的 Shell 命令。本文介绍本仓库的实际行为，逐函数调用关系见 [CALLGRAPH.md](./CALLGRAPH.md)。

## 1. s13 能后台执行，为什么还需要 s14？

s13 解决“命令已经开始执行，父循环怎样继续工作”；s14 解决“现在没有用户输入，到了某个时间怎样启动一轮 Agent 工作”。

例如，你希望每个工作日上午 9 点检查测试结果，可以登记：

```json
{
  "cron": "0 9 * * 1-5",
  "prompt": "检查工作区已有测试日志，汇报失败项和待处理问题",
  "recurring": true,
  "durable": true
}
```

模型通过 `schedule_cron` 创建定义，到期后收到该 prompt，再决定调用哪些工具。若其中需要运行慢 Bash，仍可使用 s13 的后台执行能力。

这是运行在 Harness 进程里的调度器。关闭程序后，持久定义可以保留，但不会继续触发工作。

## 2. 一次定时任务怎样从登记走到模型？

1. Agent 调用 `schedule_cron`。调度器校验参数，登记任务；需要持久化时，先完成写盘。
2. Scheduler 轮询当前时间。命中规则后设置 `pending_delivery=true`，持久任务先保存该状态，再加入队列。
3. Queue Processor 发现队列非空，尝试取得 Agent 执行锁；Agent 忙时等待。
4. 取得锁后启动一轮 Agent Loop，取出队列，将每条 prompt 作为 `[Scheduled] ...` 用户消息注入。
5. 模型首次成功响应后，调用 `acknowledge` 确认投递。
6. Agent 根据模型响应继续执行工具或输出答案，CLI 用 `[scheduled answer]` 标记自动回答。

```text
schedule_cron → 调度定义
                    │ 到期
                    ▼
             pending_delivery + 队列
                    │ Agent 执行锁可用
                    ▼
               Agent Loop → 模型首次成功响应 → acknowledge
                    │
                    └─ 继续执行工具、生成回答
```

**确认的是 prompt 的投递，不是业务任务完成。** 例如，模型先成功返回“运行测试”的工具调用，调度已经确认；之后测试失败，不会因此自动恢复这次 Cron 投递。

## 3. 三个工具与两个开关

| 工具 | 用途 |
| --- | --- |
| `schedule_cron` | 登记时间表达式和 prompt |
| `list_crons` | 查看定义，以及 recurring、durable、pending 状态 |
| `cancel_cron` | 删除定义并移除尚在队列中的待投递项 |

这些工具只注册到父 Agent。两个可选开关默认均为 `true`，含义彼此独立：

| 参数 | true | false |
| --- | --- | --- |
| `recurring` | 确认投递后保留定义，等待后续命中 | 首次确认投递后删除定义 |
| `durable` | 将定义及投递状态写入磁盘 | 只在当前进程中保留 |

`recurring=false` 表示在该 Cron 规则下一次命中并确认后删除，不表示“立即执行一次”，也不是指定某个完整日期的接口。

取消会阻止队列中尚未消费的工作，但不会中断已经启动的模型调用或工具执行。

## 4. 如何写时间规则？

本实现采用五字段表达式，使用运行进程的本地时间，默认时钟是 `datetime.now`。

```text
分钟 小时 日期 月份 星期
0-59 0-23 1-31 1-12 0-6
                     0 是星期日
```

| 表达式 | 含义 |
| --- | --- |
| `* * * * *` | 每分钟 |
| `*/15 * * * *` | 每小时的 0、15、30、45 分 |
| `0 9 * * 1-5` | 每周一到周五上午 9 点 |
| `30 18 * * *` | 每天下午 6 点半 |

这是教学版解析器，支持精确值、星号、简单区间、数值列表和 `*/n`。不要直接套用其他 Cron 系统的完整语法：这里不支持秒字段、年份、月份英文名、星期日别名 7、区间步进等形式。

步进以字段数值对 n 取模，尤其不要假定日期、月份的步进起点与其他 Cron 实现完全一致。复杂组合也应先对照解析器和测试确认。

日期和星期同时受限时采用 OR 语义。例如 `0 9 1 * 1` 会在“每月 1 日或每周一”的上午 9 点命中，而不是只在恰好为周一的每月 1 日命中。

运行服务器的本地时间未必是你电脑的时区。此版本没有每任务时区设置，也没有完善的夏令时调度策略。

## 5. 为什么需要 Scheduler 和 Queue Processor 两个线程？

| 执行位置 | 职责 |
| --- | --- |
| 主线程 | 读取用户输入，执行前台 turn |
| `cron-scheduler` | 默认每秒检查时间，只把到期任务入队 |
| `cron-queue-processor` | 默认每 0.2 秒检查队列，在 Agent 执行锁可用时启动自动 turn |

时间检查不直接调用模型，也不修改对话历史。因此，某次模型响应较慢时，Scheduler 仍能发现到期任务。

`run_turn` 与 Queue Processor 使用同一个 `_agent_lock`，把前台与定时 Agent Loop 串行化。默认 CLI 在等待输入期间，自动 turn 也可以运行。

锁串行化的是这两个循环的执行；当前 CLI 的用户消息追加发生在 `run_turn` 之前，不能由此推导出所有消息列表写入都严格处于锁内。

到期任务也不一定单独占一轮：前台 turn 开始时同样会消费队列；多条待投递 prompt 可以在同一个 turn 中注入。显式用户请求保留为当前主要请求，自动 turn 则使用调度 prompt 作为请求依据。

## 6. 防重复与失败恢复

`CronJob` 除规则和 prompt 外，还记录两个字段：

- `last_fired`：最近触发的分钟标记，避免每秒轮询在同一分钟重复入队。
- `pending_delivery`：上一次触发是否仍待确认；未确认时不会再为这个定义入队。

确认前，如果主模型请求进入不可恢复错误分支，Agent Loop 会 `restore` 重新排队，并移除本次注入的调度消息。确认成功后，重复任务清除 pending，一次性任务删除定义。

持久定义恢复时，已保存的 pending 项会重新入队。这有利于重试未确认投递，但也可能重复：例如模型已响应，进程却在确认落盘前退出。

因此，不应将它当成“业务效果恰好发生一次”的保证。需要重复执行安全的任务，应在实际操作处使用幂等键或检查已有结果。恢复逻辑也不覆盖任意位置的所有异常，不能视为完整的生产任务队列。

## 7. 持久化保存了什么？

调度器保存 durable 任务的定义、pending 状态和最近触发分钟。写入采用临时文件、flush、fsync 和原子替换，并在部分写盘失败路径上回滚内存状态。

保存的不是完整 Agent 会话：模型历史、工具执行现场和 s13 的后台 worker 不会一起恢复。文件原子替换也不提供跨进程调度协调，不应让多个独立调度器共享同一文件并期待自动合并。

还有两个容易混淆的时间边界：

- 进程关闭期间错过的时间点，不会逐个补跑。重启主要恢复已登记定义和保存为 pending 的投递。
- pending 期间错过的重复触发不会各自积累成独立任务；一个定义只有一个 pending 状态。

若首次响应已经确认，但后面的业务工作失败，一次性任务可能已经被删除。这正是“投递确认”和“执行成功”分开的含义。

## 8. 它仍使用原来的 Harness

定时 prompt 进入现有 Agent Loop，复用 Prompt、Memory、Compact、工具和恢复机制，没有再创建一套专用 Agent。

需要交互授权的工具在自动 turn 的后台线程里会被拒绝，避免抢占前台终端输入。已有的硬拒绝规则仍然生效。

`cancel_cron` 不是正在执行任务的取消令牌；停止 Cron runtime 也不是强制终止正在运行的模型和工具。当前实现没有完整的任务执行超时、隔离执行环境或业务结果重试策略。

## 9. 建议怎样阅读与验证？

1. [cron_scheduler.py](./harness/cron_scheduler.py)：先看 `CronJob`、`schedule_job`、`poll_due_jobs`。
2. 接着读 `consume_queue`、`acknowledge`、`restore`，区分出队、确认和重新排队。
3. [agent_loop.py](./harness/agent_loop.py)：看 `_queue_processor_loop`、`run_turn` 和 `waiting_for_cron_ack` 的处理。
4. [code.py](./code.py)：看 CLI 怎样启动运行时、输出自动回答并在退出时停止轮询。
5. [test_s14.py](../tests/test_s14.py)：看表达式匹配、同分钟去重、持久化恢复、确认失败和自动 turn 的测试。

在仓库根目录运行已有测试：

```bash
python3 -m unittest tests.test_s14
```

已配置模型访问时，可运行 `python3 s14_cron_scheduler/code.py`，让 Agent 创建一条每分钟检查已有日志、`recurring=false`、`durable=false` 的任务，保持 CLI 打开，观察自动回答和任务定义删除的时机。

读完后可以自问：到期为什么先入队？持久化为什么不等于关闭程序后仍能执行？为什么收到第一次模型响应就确认，会影响一次性任务的失败重试？
