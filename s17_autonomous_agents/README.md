# s17 Autonomous Agents：队友自己看板、自己认领

s16 的队友已经能收信、审批计划、等待和退出。s17 把它们接到 s12 的共享任务板上：空闲时主动发现可执行任务，认领成功后开始工作，完成后再找下一项。

**自动化的是找工作和认领，不是自动判定任务完成。** 模型仍然需要执行任务、验证结果，并调用 `complete_task` 更新看板。

本文对应本仓库当前实现。前置概念见 [s15 Agent Teams](../s15_agent_teams/README.md) 和 [s16 Team Protocols](../s16_team_protocols/README.md)。

完整执行路径见 [调用图与源码索引](./CALLGRAPH.md)，或直接查看 [SVG 调用图](./callgraph.svg)。

## 1. 为什么需要自动认领？

假设 Lead 已拆出十项任务，又启动了 Alice 和 Bob。若每完成一项都需要 Lead 再发一条分配消息，队友的下一步工作就依赖 Lead 持续协调。

s17 让 Lead 主要负责创建任务、描述验收要求和设置依赖。队友完成当前工作后扫描任务板，找到可认领任务便自行开工。

| 分工 | 负责什么 |
| --- | --- |
| Lead | 拆分任务、设置依赖、协调冲突、检查整体结果 |
| Harness | 扫描候选、保护认领、注入任务、管理空闲等待 |
| 队友模型 | 理解任务、调用工具、验证结果、明确标记完成 |
| TaskManager | 保存归属和状态，检查依赖与状态转换 |

任务按文件名排序选择，没有按角色、技能、优先级或负载匹配。给队友命名为“测试工程师”，不会自动限制它只领取测试任务。

## 2. 用三个任务理解完整流程

以两份输入文件和一个计算任务为例：

```text
A：写 alpha.txt = 21 ─┐
                     ├─ C：读取两份文件，计算乘积，写 result.txt = 42
B：写 beta.txt = 2 ───┘
```

Lead 创建 A、B，再创建 `blockedBy=[A, B]` 的 C，并启动两名队友。

1. 队友先处理启动 prompt；这一工作周期结束后进入 IDLE。
2. Alice 和 Bob 各自扫描任务板。A、B 可执行，C 仍被依赖阻塞。
3. 两名队友分别认领 A、B。认领成功会把 owner 写入任务，并将状态从 pending 改为 in_progress。
4. 模型收到包含完整任务记录的 `[Auto-claimed task]` 消息，执行文件操作、回读验证，再调用 complete_task。
5. A、B 都完成后，C 才成为候选。一名空闲队友认领它并计算结果。
6. 工作结束后队友继续找任务；持续空闲达到上限，或收到关闭请求，才退出。

依赖任务并不要求 `blockedBy` 为空，而是要求其中每项都已 completed。缺失的依赖也会阻止认领。

## 3. WORK、IDLE 和退出怎样切换？

本仓库的 s16 已有 idle 生命周期。s17 在它的等待阶段加入任务扫描和超时。

```text
WORK：收信 → 模型 → 工具循环
  │ 无工具调用，发送总结
  ▼
IDLE：先检查邮箱，再检查任务板
  ├─ 有消息 → 返回团队循环处理 → WORK 或关闭
  ├─ 成功认领任务 → 注入完整任务 → WORK
  ├─ 没有工作 → 等待后重试
  └─ 空闲超时 → 发送退出说明 → done

WORK / IDLE 收到有效关闭请求 → 回应协议 → done
运行异常 → 尝试汇报错误 → failed
```

默认设置：

| 参数 | 值 | 含义 |
| --- | --- | --- |
| 工作周期上限 | 10 轮模型调用 | 超过后汇报 error，回到 idle |
| 看板轮询间隔 | 5 秒 | 无工作时下一次检查的间隔 |
| idle 超时 | 60 秒 | 单次空闲阶段的等待上限 |

进入 IDLE 后会先立即检查一次，不是必须先等 5 秒。邮箱 Event 可以提前唤醒等待；任务板没有文件监听，新任务通常在下一次轮询发现。

60 秒是一次 idle 的时间预算，不是队友总寿命或模型请求超时。收到工作后，下次进入 idle 会重新计时。超时退出也不等于关闭协议获批，它发送独立的退出说明。

## 4. 怎样判断任务可以认领？

`scan_unclaimed_tasks` 筛选三个条件同时成立的任务：

- status 为 `pending`。
- owner 为 `None`，尚未分配。
- 所有依赖都已 `completed`。

扫描只是候选发现，不意味着获得任务所有权。多个队友可能同时看到同一个候选，因此认领时必须重新检查。

```text
扫描得到候选 A
  → claim_task(A, 自己的名字)
  → 加锁后重新读取 A
  → 再检查 status、owner 和依赖
  → 保存 owner + in_progress
  → 成功后才把任务注入模型历史
```

`claim_next` 只有在返回结果以 `Claimed ` 开头时才确认成功。如果竞争失败，它会尝试扫描结果中的下一项；不会把认领失败的任务当成自己的工作。

## 5. 两个队友怎样避免重复领取？

本实现用管理器内的线程锁和共享 `.board.lock` 文件上的 `flock`，保护创建、认领和完成任务的读改写过程。

例如 Alice 先拿到锁并认领 A，Bob 随后拿到锁重新读取时，看到的已经是 in_progress，于是认领失败。

锁文件与任务 JSON 分开，是因为任务保存使用原子替换；不能依赖一个马上会被替换的任务文件 inode 作为稳定锁对象。

这套保护要求写入方遵守同一个锁协议。直接手改任务 JSON，或使用前几章没有这套锁的管理器同时写入，仍可能绕过保护。它也不等于分布式任务队列；实际跨进程使用还依赖底层文件系统的锁语义。

原子替换解决“文件是否写完整”，认领事务锁解决“是否有两个执行者都认领成功”，两者用途不同。

## 6. 队友新增哪些工具？

在 s16 五个工具的基础上，增加三个任务工具，总计八个：

| 工具 | 队友侧行为 |
| --- | --- |
| `list_tasks` | 查看共享任务板 |
| `claim_task(task_id)` | 使用固定的队友身份认领 |
| `complete_task(task_id)` | 只允许完成归属于自己的 in_progress 任务 |

队友模型不能通过 claim_task 参数指定另一个 owner，handler 用闭包绑定自己的名字。complete_task 同样传入队友身份并校验归属；Lead 保留任务管理入口。

自动认领发生在 Harness 的 idle 流程里，不需要模型额外调用 claim_task。该工具仍可供队友主动认领使用，但不会授予创建任务、创建队友或定时调度的入口。

**输出“任务做完了”不会更新看板。** 模型必须显式调用 complete_task。该调用是状态声明，不是自动验收器；是否真的测试通过，仍需模型和 Lead 检查产物。

## 7. 身份和上下文怎样保留？

每个新工作周期开始时，若历史不超过三条，`restore_identity` 会补一条包含队友名字、角色和验证要求的提醒，并保留首条 system 的位置。

另外，队友请求模型时固定携带首条 system，加上近期消息，防止简单滑窗把身份提示挤掉。

这里没有给队友增加完整的 Compact 或 Memory。短历史只是一个启发式条件，并不能证明发生过压缩；近期消息切片也不是完整的 token 预算或工具消息配对管理。

## 8. 模块边界在哪里？

| 模块 | 职责 |
| --- | --- |
| [autonomous_agents.py](./harness/autonomous_agents.py) | idle 策略、发现工作、任务事件和身份提醒 |
| [task_system.py](./harness/task_system.py) | 候选筛选、认领事务、归属与依赖检查 |
| [agent_teams.py](./harness/agent_teams.py) | 队友模型循环、消息、任务工具和退出状态 |
| [team_protocols.py](./harness/team_protocols.py) | 沿用 s16 的关闭与审批协议 |
| [agent_loop.py](./harness/agent_loop.py) | 将 Lead 的同一个 TaskManager 注入团队管理器 |

AutonomousWorker 不直接调用模型、不直接消费邮箱，也不实现关闭握手。发现邮箱非空后，它把控制权交回团队循环，让既有协议路由处理消息。

“邮箱优先”指一次检查时已经可见的消息优先；它不是跨邮箱和任务板的原子事务。消息若恰好在检查之后到达，仍可能先发生一次认领，再在团队收信点处理关闭。

## 9. 当前实现还不保证什么？

- 没有任务租约、心跳续租和自动重新分配。队友异常、超时退出或关闭时，已认领但未完成的任务可能留在 in_progress；不会自动完成或释放。
- 队友可以在完成一个工作周期后继续领取其他候选，代码没有强制“每名队友最多持有一个未完成任务”。
- idle 到期只说明这一阶段没有拿到新工作，不代表全局任务板全部完成。其他队友仍可能忙碌，依赖也可能还没解锁。
- 一条坏任务记录可能使本次扫描失败。idle 会记录诊断并继续等待，但不会自动修复记录；锁竞争等阻塞操作也不是硬超时可中断的。
- 工作目录仍然共享。认领锁保护的是任务归属，不保护两个不同任务同时改同一份源码；工作区隔离留给后续章节。
- 任务板持久化不代表线程、上下文和协议状态可以重启恢复。
- Lead 仍按自己的收信点消费队友回报；任务板变化不会独立启动新的 Lead turn。
- 任务 owner 校验是工具路径上的约束，Bash 和共享文件访问并不构成安全沙箱。

## 10. 已完成的真实验证

2026-09-05 在 L20-Server 上使用百炼 `qwen-plus` 做过一次验证。任务创建、启动和结束检查由测试脚本编排；两名队友的推理、工具选择、文件操作和完成声明由真实模型执行。

| 检查 | 观察结果 |
| --- | --- |
| 自动认领 | Bob 领取 alpha，Alice 领取 beta，两者并行执行 |
| 依赖约束 | 两项前置任务完成后，Alice 才领取计算任务 |
| 产物验证 | alpha.txt 为 21，beta.txt 为 2，result.txt 为 42，均含换行 |
| 完成状态 | 三项任务均经模型调用 complete_task 变为 completed |
| 关闭协议 | Alice 回复关闭请求并退出，请求状态变为 approved |
| idle 超时 | Bob 使用默认 60 秒等待后发送超时说明并退出 |

本次共 13 次真实模型调用，使用量统计为 16,261 tokens。报告中七项检查均通过。这是小型功能验证，不是大型项目成功率或长时间稳定性评测，也没有验证 Lead 自主拆解任务。

当次证据位于服务器 `/data/cc-s17-live-l5r1odxb/`：

- `report.json`：检查结果、任务状态变化与最终队友状态。
- `model_calls.jsonl`：模型请求、响应和用量。
- `alpha.txt`、`beta.txt`、`result.txt`：真实产物。

这些是当次服务器上的验证文件，不随 Git 仓库分发。

## 11. 阅读与测试

推荐顺序：先读 AutonomousWorker.idle_poll，再读 TaskManager 的 scan_unclaimed_tasks 和 claim_next，接着看 claim_task 的锁内校验，最后回到队友循环查看工作、等待与退出如何衔接。

仓库根目录可运行：

```bash
python3 -m unittest tests.test_s17
python3 s17_autonomous_agents/code.py
```

CLI 需要已配置的模型访问凭据。创建带依赖的几项小任务并启动两名队友，即可观察自动认领；任务完成后可请求关闭，或保留默认 idle 超时。

实现完成时，s17 的 94 项测试和全项目的 556 项测试均通过。[test_s17.py](../tests/test_s17.py) 覆盖多管理器并发认领、竞争失败换候选、依赖解锁、归属检查、收信优先、超时、身份提醒和完整依赖链。

读完后可以自问：扫描成功为什么不等于认领成功？线程退出为什么不能顺便把任务标记完成？全局还有 pending 任务时，队友为什么仍可能 idle 超时退出？
